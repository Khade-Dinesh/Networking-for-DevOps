1. WHY THESE MODELS MATTER FOR DEVOPS
---------------------------------------------------------------

  Most people memorize OSI layers for exams and forget.
  DevOps engineers need to UNDERSTAND them to:

  → Debug network connectivity issues
  → Configure firewalls at correct layer
  → Understand load balancer types (L4 vs L7)
  → Troubleshoot why packets are dropping
  → Configure security groups correctly
  → Understand how DNS, HTTP, SSL work together
  → Design secure network architectures

  REAL DEVOPS SCENARIOS THAT NEED OSI KNOWLEDGE:

  PROBLEM                         LAYER TO INVESTIGATE
  -------                         --------------------
  Website unreachable             Layer 3 (routing/IP)
  Port connection refused         Layer 4 (TCP/firewall)
  SSL certificate error           Layer 6 (presentation)
  DNS not resolving               Layer 7 (application)
  Physical cable unplugged        Layer 1 (physical)
  Wrong MAC address               Layer 2 (data link)
  Load balancer routing issue     Layer 4 or 7

2. OSI MODEL — ALL 7 LAYERS DEEP DIVE
---------------------------------------------------------------

  OSI = Open Systems Interconnection
  Created by ISO in 1984 as a reference model.
  Describes how network communication happens
  in 7 separate, distinct layers.

  COMPLETE LAYER BREAKDOWN:

  ════════════════════════════════════════════════════════════
  LAYER 7 — APPLICATION
  ════════════════════════════════════════════════════════════

  What it does:
  → Interface between user applications and network
  → Provides network services directly to end users
  → NOT the application itself — the interface to network

  Protocols:
    HTTP    → Web browsing (port 80)
    HTTPS   → Secure web browsing (port 443)
    FTP     → File transfer (port 21)
    SMTP    → Email sending (port 25)
    IMAP    → Email receiving (port 143)
    DNS     → Domain name resolution (port 53)
    SSH     → Secure remote access (port 22)
    DHCP    → Automatic IP assignment (port 67/68)
    SNMP    → Network management (port 161)
    LDAP    → Directory services (port 389)

  DevOps relevance:
  → HTTP status codes (200, 404, 500) live here
  → API endpoints and REST calls happen here
  → Load balancer rules based on URL = Layer 7
  → AWS Application Load Balancer (ALB) works here
  → Web Application Firewall (WAF) works here

  Data unit: Data / Message

  ════════════════════════════════════════════════════════════
  LAYER 6 — PRESENTATION
  ════════════════════════════════════════════════════════════

  What it does:
  → Translates data between application and network
  → Handles encryption and decryption
  → Handles compression and decompression
  → Handles data format conversion
  → Ensures data is in readable format for application

  Functions:
    Encryption   → SSL/TLS encrypts data here
    Decryption   → Recipient decrypts here
    Compression  → Reduces data size for transfer
    Encoding     → ASCII, Unicode, EBCDIC conversion
    Serialization → JSON, XML, protobuf formatting

  Protocols/Formats:
    SSL/TLS   → encryption for HTTPS
    JPEG      → image compression
    MPEG      → video compression
    MP3       → audio compression
    ASCII     → text encoding
    Unicode   → international text encoding

  DevOps relevance:
  → SSL/TLS certificates managed here
  → HTTPS termination at load balancer = Layer 6
  → Data serialization (JSON/XML) for APIs
  → Certificate errors = Layer 6 problem

  Data unit: Data

  ════════════════════════════════════════════════════════════
  LAYER 5 — SESSION
  ════════════════════════════════════════════════════════════

  What it does:
  → Establishes, manages and terminates sessions
  → Keeps different applications sessions separate
  → Manages dialog control between systems
  → Handles session recovery if connection drops

  Functions:
    Session establishment → create connection
    Session maintenance   → keep connection alive
    Session termination   → cleanly close connection
    Synchronization       → checkpoints in data transfer
    Dialog control        → half-duplex or full-duplex

  Examples:
    Login sessions on websites
    Database connection sessions
    API sessions with tokens
    Video call sessions
    RPC (Remote Procedure Calls)

  Protocols:
    NetBIOS  → Windows session management
    RPC      → Remote Procedure Call
    PPTP     → Point-to-Point Tunneling Protocol
    SIP      → Session Initiation Protocol (VoIP)

  DevOps relevance:
  → Session tokens in web applications
  → Database connection pooling
  → Keep-alive connections in HTTP
  → WebSocket connections

  Data unit: Data

  ════════════════════════════════════════════════════════════
  LAYER 4 — TRANSPORT
  ════════════════════════════════════════════════════════════

  What it does:
  → End-to-end communication between applications
  → Segmentation of data into smaller pieces
  → Reassembly of segments at destination
  → Flow control — prevents sender overwhelming receiver
  → Error detection and retransmission
  → Port numbers to identify applications

  THE TWO KEY PROTOCOLS:

  TCP (Transmission Control Protocol):
  → Connection-oriented (3-way handshake first)
  → Reliable — guarantees delivery
  → Ordered — packets arrive in sequence
  → Error checking and retransmission
  → Flow control and congestion control
  → Slower but reliable
  → Use when accuracy matters
  → HTTP, HTTPS, SSH, FTP, email all use TCP

  UDP (User Datagram Protocol):
  → Connectionless (no handshake)
  → Unreliable — no delivery guarantee
  → No ordering — packets may arrive out of order
  → No retransmission
  → Faster — less overhead
  → Use when speed matters more than accuracy
  → DNS, video streaming, gaming, VoIP use UDP

  PORT NUMBERS LIVE HERE:
  → Source port: random ephemeral (49152-65535)
  → Destination port: well-known service port

  DevOps relevance:
  → Firewall rules operate at Layer 4 (TCP/UDP ports)
  → AWS Network Load Balancer (NLB) works at Layer 4
  → Security Group rules specify ports = Layer 4
  → Network ACL rules = Layer 4
  → TCP vs UDP choice for services

  Data unit: Segment (TCP) / Datagram (UDP)

  ════════════════════════════════════════════════════════════
  LAYER 3 — NETWORK
  ════════════════════════════════════════════════════════════

  What it does:
  → Logical addressing using IP addresses
  → Routing packets from source to destination
  → Path determination across multiple networks
  → Packet forwarding through routers

  Functions:
    Logical addressing → IP addresses assigned here
    Routing            → finds best path to destination
    Path determination → OSPF, BGP routing protocols
    Packet forwarding  → router sends packet toward dest
    Fragmentation      → splits packets if too large

  Key Protocols:
    IP (IPv4/IPv6)  → logical addressing
    ICMP            → error messages and ping!
    ARP             → resolves IP to MAC address
    OSPF            → routing within organization
    BGP             → routing between internet providers
    RIP             → older routing protocol

  DevOps relevance:
  → VPC, subnets, CIDR blocks = Layer 3 concepts
  → Route tables in AWS = Layer 3
  → IP addressing for all infrastructure
  → ping command uses ICMP = Layer 3
  → traceroute shows Layer 3 path

  Data unit: Packet

  ════════════════════════════════════════════════════════════
  LAYER 2 — DATA LINK
  ════════════════════════════════════════════════════════════

  What it does:
  → Physical addressing using MAC addresses
  → Node-to-node delivery on same network segment
  → Error detection in physical transmission
  → Controls how data is placed on physical medium
  → Divided into two sub-layers: LLC and MAC

  Sub-layers:
    LLC (Logical Link Control)
    → Communication between network and data link layer
    → Flow control and error control

    MAC (Media Access Control)
    → Hardware address management
    → Controls access to physical medium

  Key Protocols:
    Ethernet  → wired LAN standard
    WiFi      → wireless LAN (802.11)
    PPP       → Point-to-Point Protocol
    VLAN      → Virtual LAN segmentation
    ARP       → Address Resolution Protocol

  MAC Address:
  → 48-bit hardware address (6 groups of hex)
  → Example: 00:1A:2B:3C:4D:5E
  → First 3 groups = manufacturer OUI
  → Last 3 groups = device specific
  → Unique to every network interface card

  DevOps relevance:
  → Switch operates at Layer 2
  → VLANs for network segmentation
  → MAC filtering for access control
  → Less relevant in cloud (abstracted away)

  Data unit: Frame

  ════════════════════════════════════════════════════════════
  LAYER 1 — PHYSICAL
  ════════════════════════════════════════════════════════════

  What it does:
  → Transmits raw bits (0s and 1s) over physical medium
  → Defines physical characteristics of network
  → Specifies cables, connectors, voltages, frequencies
  → No addressing — just raw signal transmission

  Physical mediums:
    Copper cable    → electrical signals (Cat5e, Cat6)
    Fiber optic     → light signals (fastest!)
    WiFi            → radio waves
    Bluetooth       → short range radio
    Coaxial cable   → older cable type

  Devices at Layer 1:
    Hub         → broadcasts to all ports (dumb!)
    Repeater    → amplifies signal over long distance
    Modem       → modulates/demodulates signals
    Network cable, connectors, fiber

  DevOps relevance:
  → Data center hardware considerations
  → AWS Direct Connect physical connection
  → Network speed depends on physical medium
  → Usually abstracted in cloud — least concern

  Data unit: Bits (0s and 1s)

  MEMORY TRICKS:

  Top to Bottom (Layer 7 → 1):
  "All People Seem To Need Data Processing"
  Application → Presentation → Session →
  Transport → Network → Data Link → Physical

  Bottom to Top (Layer 1 → 7):
  "Please Do Not Throw Sausage Pizza Away"
  Physical → Data Link → Network → Transport →
  Session → Presentation → Application

3. TCP/IP MODEL — ALL 4 LAYERS DEEP DIVE
---------------------------------------------------------------

  TCP/IP = Transmission Control Protocol / Internet Protocol
  The ACTUAL model that runs the internet today.
  More practical than OSI. What operating systems implement.
  Developed by DARPA in 1970s for ARPANET.

  ════════════════════════════════════════════════════════════
  LAYER 4 — APPLICATION (Combines OSI 5+6+7)
  ════════════════════════════════════════════════════════════

  Handles everything the user interacts with.
  Applications, data formatting, sessions.

  Protocols:
  HTTP, HTTPS, FTP, SSH, DNS, SMTP, IMAP,
  DHCP, SNMP, Telnet, NTP, LDAP

  ════════════════════════════════════════════════════════════
  LAYER 3 — TRANSPORT (Same as OSI Layer 4)
  ════════════════════════════════════════════════════════════

  End-to-end communication.
  Port numbers, segmentation, reliability.

  Protocols: TCP, UDP

  ════════════════════════════════════════════════════════════
  LAYER 2 — INTERNET (Same as OSI Layer 3)
  ════════════════════════════════════════════════════════════

  Logical addressing and routing.
  IP addresses and packet forwarding.

  Protocols: IP, ICMP, ARP, OSPF, BGP

  ════════════════════════════════════════════════════════════
  LAYER 1 — NETWORK ACCESS (Combines OSI 1+2)
  ════════════════════════════════════════════════════════════

  Physical transmission and local network delivery.
  MAC addresses, physical medium.

  Protocols: Ethernet, WiFi, MAC

4. ENCAPSULATION & DECAPSULATION
---------------------------------------------------------------

  ENCAPSULATION (Sender — Top to Bottom):
  Each layer adds its own header (wrapper) to the data.

  APPLICATION LAYER:
  [HTTP Data / Request]

  TRANSPORT LAYER adds TCP header:
  [TCP Header | HTTP Data]  → called SEGMENT

  NETWORK LAYER adds IP header:
  [IP Header | TCP Header | HTTP Data]  → called PACKET

  DATA LINK LAYER adds Frame header + trailer:
  [Frame Header | IP Header | TCP Header | HTTP Data | FCS]
  → called FRAME

  PHYSICAL LAYER:
  Converts entire frame to BITS (0s and 1s) → transmits

  DECAPSULATION (Receiver — Bottom to Top):
  Each layer removes its header and passes up.

  PHYSICAL:     Receives bits → converts to frame
  DATA LINK:    Removes frame header → passes packet up
  NETWORK:      Removes IP header → passes segment up
  TRANSPORT:    Removes TCP header → passes data up
  APPLICATION:  Receives original HTTP data!

  HEADERS AT EACH LAYER:

  LAYER       HEADER CONTAINS
  -----       ---------------
  Transport   Source port, dest port, seq number, checksum
  Network     Source IP, dest IP, TTL, protocol
  Data Link   Source MAC, dest MAC, EtherType, FCS

5. HOW THE INTERNET WORKS — FULL JOURNEY
---------------------------------------------------------------

  You type: https://www.google.com → press Enter

  STEP 1: BROWSER CACHE CHECK
  → Browser checks local cache for google.com IP
  → OS checks hosts file (/etc/hosts)
  → OS checks DNS cache
  → If found → skip to Step 4
  → If not found → go to Step 2

  STEP 2: DNS RESOLUTION (Layer 7)
  → Browser asks OS DNS resolver
  → OS asks configured DNS server (8.8.8.8 or ISP)
  → DNS recursive resolver checks its cache
  → If not cached → asks Root DNS server
  → Root says "ask .com TLD server"
  → TLD server says "ask google.com nameserver"
  → google.com nameserver returns: 142.250.180.46
  → Answer cached for TTL duration
  → Browser now has IP: 142.250.180.46

  STEP 3: TCP CONNECTION (Layer 4)
  → Browser initiates 3-way handshake
  → SYN sent to 142.250.180.46:443
  → SYN-ACK received from Google
  → ACK sent back
  → TCP connection established!

  STEP 4: TLS HANDSHAKE (Layer 6) — for HTTPS
  → Browser sends TLS ClientHello
  → Server sends certificate + ServerHello
  → Browser verifies certificate with CA
  → Both agree on encryption algorithm
  → Encrypted session established!
  → All data from here is encrypted

  STEP 5: HTTP REQUEST (Layer 7)
  → Browser sends:
    GET / HTTP/1.1
    Host: www.google.com
    User-Agent: Chrome/120
    Accept: text/html

  STEP 6: PACKET JOURNEY (Layers 1-3)
  → HTTP request wrapped in TCP segment
  → TCP segment wrapped in IP packet
  → IP packet wrapped in Ethernet frame
  → Frame converted to bits
  → Bits travel through:
    Your device → home router → ISP → internet backbone
    → Google's ISP → Google's data center → Google server

  STEP 7: SERVER PROCESSES REQUEST (Layer 7)
  → Google's load balancer receives request
  → Routes to available web server
  → Web server generates HTML response
  → Response travels back same path in reverse

  STEP 8: BROWSER RENDERS
  → Browser receives HTML
  → Parses HTML → finds CSS, JS, images
  → Makes additional requests for resources
  → Renders final webpage you see!

  TIME TAKEN: ~50-200 milliseconds for all of this!

6. HOW SEARCH WORKS — GOOGLE EXAMPLE
---------------------------------------------------------------

  PHASE 1: WEB CRAWLING
  → Googlebot crawls websites following links
  → Reads and stores content of pages
  → Discovers new pages through links
  → Crawl frequency based on page importance

  PHASE 2: INDEXING
  → Google processes crawled pages
  → Extracts keywords, content, metadata
  → Stores in massive distributed index database
  → Billions of pages indexed!

  PHASE 3: YOUR SEARCH REQUEST
  You type: "DevOps tutorial" → press Enter

  Network journey (as described above):
  → DNS resolves google.com to IP
  → TCP connection to Google server
  → HTTPS encrypted session
  → HTTP POST request with search query

  PHASE 4: RANKING ALGORITHM
  → Google's algorithm processes your query
  → Checks index for matching pages
  → Ranks by: relevance, authority, freshness
  → Considers: PageRank, backlinks, user signals
  → Personalizes based on: location, history
  → Runs in ~100 milliseconds!

  PHASE 5: RESULTS DELIVERED
  → Google returns JSON with search results
  → Browser renders results page
  → You see ranked list of websites

  PHASE 6: YOU CLICK A RESULT
  → Another complete DNS + TCP + HTTPS cycle
  → This time to the website you clicked!

  KEY INSIGHT FOR DEVOPS:
  Every search = multiple network requests.
  DNS lookup → TCP handshake → TLS → HTTP request
  Each step can be a point of failure or latency!

7. TCP 3-WAY HANDSHAKE — DEEP DIVE
---------------------------------------------------------------

  PURPOSE:
  Establishes reliable connection before data transfer.
  Both sides confirm they can send AND receive.

  THE 3 STEPS:

  CLIENT                          SERVER
    |                               |
    |-------- SYN (seq=100) ------->|
    |         "I want to connect,   |
    |          my sequence is 100"  |
    |                               |
    |<--- SYN-ACK (seq=200,ack=101)-|
    |         "OK! My sequence is   |
    |          200, I got your 100, |
    |          expecting 101 next"  |
    |                               |
    |-------- ACK (ack=201) ------->|
    |         "Got it! Expecting    |
    |          201 from you next"   |
    |                               |
    |    CONNECTION ESTABLISHED!    |
    |    Data transfer begins...    |

  SYN = Synchronize sequence numbers
  ACK = Acknowledge receipt

  WHY SEQUENCE NUMBERS MATTER:
  → Track which packets have been received
  → Allow reordering of out-of-order packets
  → Detect missing packets for retransmission
  → Prevent old duplicate packets from confusing

  TCP CONNECTION TERMINATION (4-Way):

  CLIENT                          SERVER
    |                               |
    |--------- FIN --------------->|   "I'm done sending"
    |<-------- ACK -----------------|   "Got it"
    |<-------- FIN -----------------|   "I'm done too"
    |--------- ACK --------------->|   "Got it"
    |                               |
    |      CONNECTION CLOSED!       |

  TCP FLAGS:
  SYN → Synchronize (start connection)
  ACK → Acknowledge (confirm receipt)
  FIN → Finish (end connection)
  RST → Reset (abort connection immediately)
  PSH → Push (send data immediately)
  URG → Urgent (priority data)

  COMMON TCP STATES:
  LISTEN      → Server waiting for connections
  SYN_SENT    → Client sent SYN, waiting for SYN-ACK
  ESTABLISHED → Connection active, data transferring
  CLOSE_WAIT  → Received FIN, waiting to close
  TIME_WAIT   → Closed but waiting for stray packets
  CLOSED      → No connection

  VIEWING TCP CONNECTIONS IN LINUX:
  netstat -an | grep ESTABLISHED   → active connections
  netstat -an | grep LISTEN        → listening ports
  ss -tulpn                        → modern replacement
  ss -s                            → summary statistics

8. OSI vs TCP/IP COMPARISON
---------------------------------------------------------------

  OSI MODEL              TCP/IP MODEL
  ---------              ------------
  7. Application    ─┐
  6. Presentation    ├──→ 4. Application
  5. Session        ─┘
  4. Transport      ────→ 3. Transport
  3. Network        ────→ 2. Internet
  2. Data Link      ─┐
  1. Physical       ─┴──→ 1. Network Access

  FULL COMPARISON TABLE:

  ASPECT          OSI                     TCP/IP
  ------          ---                     ------
  Layers          7                       4
  Created by      ISO (1984)              DARPA (1970s)
  Type            Reference/conceptual    Practical/implemented
  Approach        Generic, protocol-free  Protocol specific
  Usage           Teaching, understanding Real internet
  Reliability     Defined at layer 4      Same
  Flexibility     More flexible           Less flexible
  Industry use    Troubleshooting ref     Actual implementation

  WHICH ONE MATTERS MORE?
  → OSI: better for UNDERSTANDING and TROUBLESHOOTING
  → TCP/IP: what actually RUNS on all devices
  → DevOps engineers need BOTH perspectives!

10. KEY TAKEAWAYS FROM DAY 23
---------------------------------------------------------------

  [01] OSI has 7 layers — theoretical reference model.
       TCP/IP has 4 layers — practical real world model.
       Learn OSI to understand. TCP/IP is what actually runs!

  [02] Memory trick Top→Bottom: "All People Seem To Need
       Data Processing" (App,Pres,Sess,Trans,Net,DL,Phys)

  [03] Every web request starts with DNS resolution!
       DNS is Layer 7. Without DNS nothing works.
       DNS failure = website unreachable even if server is up!

  [04] TCP 3-way handshake: SYN → SYN-ACK → ACK
       This happens BEFORE any data is transferred.
       Every TCP connection starts with this 3-step dance!

  [05] TCP = reliable ordered delivery (accuracy matters)
       UDP = fast unordered delivery (speed matters)
       HTTP/HTTPS/SSH = TCP | DNS/Video/Gaming = UDP

  [06] Encapsulation adds headers going DOWN the stack.
       Decapsulation removes headers going UP the stack.
       Each layer only reads its own header!

  [07] Layer 3 (Network) = IP addresses and routing.
       Layer 4 (Transport) = ports and TCP/UDP.
       Layer 7 (Application) = what your app sees.
       These 3 layers matter MOST for DevOps!

  [08] AWS ALB (Application LB) works at Layer 7.
       Can route based on URL path and hostname.
       AWS NLB (Network LB) works at Layer 4.
       Routes based on TCP port and IP only!

  [09] Security Groups and NACLs operate at Layer 4.
       WAF operates at Layer 7 (HTTP inspection).
       Understanding layers = knowing which tool to use!

  [10] TTL (Time To Live) in IP packets prevents
       infinite routing loops. Each router decrements TTL.
       When TTL = 0 → packet dropped → ICMP error sent!

  [11] A complete web search involves:
       DNS → TCP handshake → TLS → HTTP → routing →
       server processing → response → render
       Each step = potential point of failure to debug!

  [12] Troubleshooting tip — think bottom up:
       Physical OK? → Layer 2 OK? → IP reachable (ping)?
       → Port open (telnet/nc)? → App responding (curl)?
       This systematic approach solves 90% of issues!
